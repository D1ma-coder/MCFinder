Движок рассчитывает точную **координату Y точки размещения особняка в Java 26.2** через оригинальный генератор Minecraft. Прежняя климатическая оценка доступна отдельно.

Для сида `4743858`, начала чанка X=1792, Z=-2416, Minecraft возвращает **Y=158**. Точка размещения структуры — X=1799, Y=158, Z=-2409. Раньше климатическая оценка давала около 172,4; это не была фактическая высота размещения.

## Подготовка

Нужны JDK 25 или новее и Python 3.9+. Из папки исходников:

```sh
python3 scripts/prepare-terrain.py --java-home /путь/к/jdk
```

Скрипт скачивает официальный серверный архив Minecraft 26.2, сверяет SHA-1 с метаданными Mojang и SHA-256 вложенных jar, компилирует адаптер и печатает путь к `runtime.json`. Свою папку кэша можно задать через `--directory PATH`. Для подготовки без сети используйте `--server-jar FILE --manifest FILE` с оригинальными метаданными этой версии.

Движок проверяет контрольные суммы подготовленных файлов и исходников адаптера. Игровые jar хранятся локально и не входят в архивы релизов. Java-процесс не запускает сервер, не создаёт игровой мир и при поиске не использует сеть. Подготовка выполняется отдельно от сборки Rust.

## Поиск

```sh
./target/release/mcfinder search \
  --script examples/scripts/high-mansion-exact.rhai \
  --terrain-runtime /полный/путь/runtime.json \
  --experimental --cores 10 --max-results 3 --count 1000000000 --ui tui \
  --output exact-mansions.jsonl --checkpoint exact-mansions.checkpoint.json
```

В Windows используйте `mcfinder.exe` и одну строку. Пример ищет Y≥190 в квадрате радиуса 262144 блока. Радиус меняется вторым аргументом `high_mansion_exact()`; предел — 30000000. Он задаётся независимо от `Query.radius`.

Результат содержит целочисленные `base_y`, `mansion:{x,y,z}`, оригинальную точку `structure_anchor:{x,y,z}` и `height_validation:"vanilla_26.2_structure_start"`. TUI помечает такую высоту как точную. Путь к runtime сохраняется в checkpoint; при переносе на другой компьютер его нужно обеспечить там.

При переборе всех старших битов без лимита результатов находки выводятся сразу, без ожидания остальных миров этой основы.

В `serve` передавайте абсолютный путь в `settings.terrain_runtime`. События раз в секунду, пауза и остановка используют обычный протокол backend. Уже отправленный Java расчёт может завершиться после паузы; новых проверок движок не начинает до продолжения. При отмене поиска Java-процесс завершается после остановки работников.

## API скриптов

| Функция | Результат |
|---|---|
| `world.mansion_base_y_exact(x,z)` | Целая Y точки размещения для чанка X/Z либо `()`, если рельеф слишком низок. Сам по себе вызов не подтверждает позицию размещения особняка и подходящий биом. |
| `world.surface_y_exact(x,z)` | Оригинальная первая занятая Y для `WORLD_SURFACE_WG`, используемая размещением структур. Это не высота мира после декораций. |
| `world.high_mansion_exact(min_y,radius)` | Первый особняк в квадрате, прошедший точный высотный и оригинальный биомный фильтры, либо `()`. Порог 60..319, радиус 0..30000000 блоков. |

Без подходящего runtime эти методы возвращают ошибку. Подмена точного расчёта оценкой не выполняется. Методы `mansion_base_y_estimate` и `high_mansion_in_square` сохраняют прежний приблизительный смысл.

## Оптимизация

1. Rust вычисляет кандидатов размещения особняка по регионам.
2. Java проверяет все возможные высоты биома выше порога. Если ни на одной нельзя разместить особняк, расчёт рельефа пропускается. Горизонтальные расчёты повторно используются между высотами, если Minecraft пометил их как горизонтальные либо их формула не зависит от Y. Неизвестные формулы вычисляются оригинальным способом.
3. Оставшиеся позиции проверяются оригинальным `getFirstOccupiedHeight(WORLD_SURFACE_WG)` с оригинальным поворотом здания. Первый угол ниже порога сразу отклоняет кандидата. Для принятого результата вычислены все четыре угла, возвращается их минимум.
4. Биом проверяется в оригинальной точке размещения на полученной высоте и по оригинальному тегу допустимых биомов особняка.

Кандидаты передаются пакетами по 32; пакет завершается после первого принятого результата. Один постоянно работающий JVM обслуживает параллельные запросы. Реестры загружаются один раз, состояния шумов сидов кэшируются с ограничением размера, климатические кэши принадлежат отдельным потокам Java. Целые чанки, части особняка и игровой мир не создаются. Климатическая оценка высоты не участвует в отбрасывании кандидатов точного режима.

## Проверка

```sh
python3 tests/vanilla_terrain.py /полный/путь/runtime.json --samples 2048 --threads 4
MCF_TERRAIN_RUNTIME=/полный/путь/runtime.json \
  cargo test --no-default-features --test exact_terrain -- --ignored
```

Проверка сравнивает принятие кандидатов и целую Y с исходным методом `WoodlandMansionStructure.findValidGenerationPoint`: пороги 60, 150, 170, 190; отрицательные координаты, границы мира и сиды со старшим установленным битом. Замер использует одинаковые координаты и сиды, прогрев обоих методов, чередование порядка и медиану трёх проходов. Запуск JVM исключён, обмен JSONL включён.

Замеры на Apple M2 Pro / JDK 27: [исходные результаты](benchmarks/vanilla-26.2-m2-pro.json). Это проверки кандидатов в секунду на данном наборе, а не сиды или сгенерированные чанки. Точный режим дороже климатической оценки; скорость зависит от частоты отсева по биому и высоте.

Четыре потока, 2057 позиций на проход, 8228 проверок отдельных позиций и 195 проверок пакетов; все сравнения совпали.

| Порог | Исходный метод, кандидатов/с | Точный фильтр, кандидатов/с | Пакеты по 32, кандидатов/с |
|---|---:|---:|---:|
| Y≥150 | 530 | 43,749 | 53,815 |
| Y≥190 | 536 | 52,011 | 61,584 |

## Границы точности

Поддержаны **Java 26.2, новый обычный Overworld и высота размещения особняка**. Датапаки, amplified/large biomes, смешивание старых чанков, изменения рельефа и итоговая видимая высота булыжной основы сюда не входят. У других структур свои правила размещения, для них нужны отдельные адаптеры. Чужие версии отклоняются, а не рассчитываются по правилам 26.2.

Точность означает совпадение с решением Minecraft при этих настройках. Она не означает мгновенный перебор целого мира или доказанный максимум производительности.

## Прогресс каждого сида

Длительные `high_mansion_exact()` и нативные приблизительные сканы особняков передают `state.active_seeds` в каждом событии progress. Запись содержит точные десятичные строки `seed_bits`, `regions_checked`, `total_regions`, игровой `seed`, индексы `region_x`, `region_z` и время проверки. TUI показывает отдельные полосы после первой секунды; при маленьком окне выводит столько, сколько помещается. Считаются просмотренные регионы размещения, а не сгенерированные чанки. Завершённая проверка удаляется из списка. `Committed` — безопасный завершённый префикс сидов; `Started` включает ещё работающие проверки.

Без `--cores` используются все доступные потоки CPU. Без `--max-results` лимита результатов нет. Для всего 64-битного пространства: `--structure-seeds --start 0 --count 281474976710656 --upper-count 65536`. Это все 2^48 основ с каждой из 2^16 комбинаций старших битов. Checkpoint фиксирует полностью завершённые основы; после остановки незавершённые проверки старших битов могут повториться.
